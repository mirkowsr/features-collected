# Lesson 10.5 — The N+1 problem: how your ORM actually fetches relations

**Goal:** Recognize the #1 real-world ORM querying issue, and know exactly which SQL each Drizzle fetching style emits.

---

## Theory

### The problem

Your app needs orders *with* their customers. The naive shape — one query for orders, then one query per order's customer:

```
SELECT * FROM sales.orders;                          -- 1 query   (1000 orders)
SELECT * FROM sales.customers WHERE customerid = 1;  -- ┐
SELECT * FROM sales.customers WHERE customerid = 2;  -- ├ 1000 queries
...                                                  -- ┘
```

**1 + N queries** for N rows. Each query is a network round-trip plus parse/plan on the server. At 1ms round-trip, 1,000 rows = **~1 second of pure overhead** — for data a single join returns in ~10ms. It also hammers the connection pool and scales linearly with row count: fine in dev (10 rows), meltdown in production (100k).

The insidious part: the code *looks* clean. Nobody wrote "1000 queries" — the loop hides it.

### The three fixes (and what each emits)

| Approach | Queries | Result shape | Watch out for |
|----------|---------|--------------|---------------|
| Naive loop | 1 + N ❌ | nested | everything |
| **Batch** `WHERE customerid IN (...)` | 2 | two flat lists, stitch in app | huge IN lists; manual stitching |
| **Explicit join** | 1 | flat rows, **parent columns repeated** per child | dedupe/reduce in app code |
| **Drizzle relational API** (`findMany({ with })`) | 1 | nested ✅ | a *heavy* single query — see below |

### What Drizzle actually emits

**1. Explicit join — you write the SQL shape:**

```ts
const rows = await db
  .select()
  .from(orders)
  .leftJoin(customers, eq(orders.customerid, customers.customerid))
// → SELECT ... FROM sales.orders LEFT JOIN sales.customers ON ...
// one flat row per order; customer columns duplicated on every row
```

**2. Relational query — Drizzle writes a cleverer SQL shape:**

```ts
await db.query.orders.findMany({ with: { customer: true } })
```

This is **not** N+1 (that was old-generation ORMs with lazy loading). Drizzle emits *one* query using `LEFT JOIN LATERAL` + JSON aggregation (simplified):

```sql
SELECT o.*, c.data AS customer
FROM sales.orders o
LEFT JOIN LATERAL (
  SELECT json_build_array(...) AS data
  FROM sales.customers
  WHERE customers.customerid = o.customerid LIMIT 1
) c ON true;
```

So the trade-off isn't "1+N vs 1" — it's **simple join vs one complex query**:

- ✅ nested result, no app-side dedupe; fetches only the columns you `select`
- ❌ harder for Postgres to optimize on big result sets; JSON building costs CPU; easy to drag a whole object graph (`with: { customer: { with: { ... } } }`) into one monster query

**3. The real N+1 trap in Drizzle** is hand-written:

```ts
const allOrders = await db.select().from(orders)
for (const o of allOrders) {
  o.customer = await db.query.customers.findFirst({
    where: eq(customers.customerid, o.customerid),
  }) // ← one query PER ORDER. N+1, by hand.
}
```

### How to catch it

You can't fix what you can't count:

- **Dev:** enable Drizzle's query logger (`drizzle(..., { logger: true })`) — a page render should be a handful of queries, not hundreds.
- **Prod:** `pg_stat_statements` (lesson 27.5). The N+1 signature: one normalized query (`WHERE customerid = $1`) with `calls` in the thousands per request.
- **Always:** before trusting any abstraction, run it and `.toSQL()` it.

## Worked example — same data, three ways

Fetch 100 orders with customer names, and count queries:

```ts
// A — naive loop: 101 queries ❌
const os = await db.select().from(orders).limit(100)
for (const o of os) {
  await db.select().from(customers).where(eq(customers.customerid, o.customerid))
}

// B — batch: 2 queries, stitch yourself
const os = await db.select().from(orders).limit(100)
const cs = await db.select().from(customers)
  .where(inArray(customers.customerid, os.map((o) => o.customerid)))
const byId = new Map(cs.map((c) => [c.customerid, c]))
const result = os.map((o) => ({ ...o, customer: byId.get(o.customerid) }))

// C — relational API: 1 query, nested result, JSON-aggregation SQL
const result = await db.query.orders.findMany({
  limit: 100,
  with: { customer: true },
})

console.log(db.query.orders.findMany({ with: { customer: true } }).toSQL())
// ← always look at what you're actually sending to Postgres
```

On the `bigsalesdb` (lesson 22.5) volumes, measure A vs C with `\timing` or query logs — the difference is not subtle.

## Exercises

1. Write version A (naive loop) against `salesdb` with `logger: true`. Count the logged queries for 10 orders. Now point it at `bigsalesdb` with no `LIMIT` — how many queries *would* that be? Why did dev never hurt?

2. Write version C, print `.toSQL()`, and run the emitted SQL by hand in `psql`. Find the `LATERAL` and the JSON function. Why did Drizzle choose `LIMIT 1` inside the lateral subquery for a many-to-one relation?

3. Write the explicit-join version, then reduce the flat rows into the same nested shape as C in TypeScript. Now fetch only `firstname` and `score` from customers in all three versions — which version made column selection easiest? Which fetched the most bytes by default?

4. Run version A against `bigsalesdb`, then check `pg_stat_statements` (lesson 27.5). Find the N+1 signature: which query row, and what does its `calls` count tell you? Reset stats (`SELECT pg_stat_statements_reset();`), run version C, and compare.

5. `EXPLAIN ANALYZE` (lesson 27) the SQL from versions B, C, and the join against `bigsalesdb` for 1,000 orders. Compare `actual time` and total bytes fetched. At what result size does the relational API's JSON building start to lose to the plain join?

6. **Pagination interplay (lesson 09.5):** version C with `limit: 100` paginates *orders* — but what happens if you also nest `with: { customer: { with: { ... } } }` and one relation is unbounded? Design the endpoint: keyset-paginated orders + bounded relations. Which knob (`limit`, `columns`) goes where?

7. **Predict before you run:** two endpoints need "customer with their 5 most recent orders". Write it with the relational API (`with: { orders: { orderBy, limit: 5 } }`) and with `DISTINCT ON` (lesson 15.5). Print both SQL statements. Which gives Postgres more freedom, and which gives you a nested result for free?
