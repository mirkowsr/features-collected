# Lesson 06.5 — Data types in practice: money, time, IDs & text

**Goal:** Choose the right column type the first time — the four decisions that bite real applications are money, timestamps, primary keys, and text.

---

## Theory

Lesson 06 listed the types. This lesson is about the **choices that go wrong in production**.

### Money: `NUMERIC`, never `FLOAT`

| Type | Behaviour | Verdict |
|------|-----------|---------|
| `NUMERIC(p,s)` / `DECIMAL` | exact decimal arithmetic | ✅ money, quantities, scores |
| `REAL` / `DOUBLE PRECISION` | binary floating point, **rounding errors** | ❌ never for money |
| `INT` (cents) | exact, but every query must divide by 100 | valid, but awkward |

```sql
SELECT 0.1::float8 + 0.2::float8;     -- 0.30000000000000004
SELECT 0.1::numeric + 0.2::numeric;   -- 0.3
```

`salesdb` stores `price`/`sales` as `INT` — fine for a toy dataset, but the first time you need cents you'll have to migrate the type (exercise 1).

### Time: `TIMESTAMPTZ`, almost always

| Type | Stores | Trap |
|------|--------|------|
| `TIMESTAMP` | a wall-clock value, **no timezone** | "3pm" — 3pm *where?* |
| `TIMESTAMPTZ` | an absolute instant (UTC), displayed in the session's timezone | none for app data |

```sql
SET timezone = 'UTC';
SELECT now();                          -- 2025-01-15 10:00:00+00
SET timezone = 'Europe/Berlin';
SELECT now();                          -- same instant, shown as 11:00:00+01
```

`TIMESTAMPTZ` stores **one** value (UTC) and converts on display. `TIMESTAMP` stores whatever wall-clock string you gave it and hopes everyone agrees what zone it meant. Rule: `TIMESTAMPTZ` for anything that *happened*; `DATE` for calendar concepts (birthdays); plain `TIMESTAMP` almost never.

### Primary keys: `IDENTITY` vs `SERIAL` vs `UUID`

| Choice | Pros | Cons |
|--------|------|------|
| `GENERATED ALWAYS AS IDENTITY` | SQL-standard, compact, fast, sortable | guessable, leaks row counts, awkward for distributed inserts |
| `SERIAL` | same as identity (it's the legacy syntax) | non-standard, permissions quirk on the sequence |
| `UUID` (`gen_random_uuid()`) | unguessable, mergeable across systems, safe in URLs | 16 bytes, random order hurts B-tree inserts, ugly to read |

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY   -- default choice
id UUID PRIMARY KEY DEFAULT gen_random_uuid()        -- when IDs are public-facing
```

### Text: `TEXT` as default

In Postgres, `VARCHAR(n)` and `TEXT` have **identical performance**. `VARCHAR(n)` only adds a length *constraint*. So: use `TEXT`, and express real rules as `CHECK (length(email) <= 254)` if needed — changing a `CHECK` later doesn't rewrite the table, changing `VARCHAR(50)` → `VARCHAR(100)` can.

### NULL discipline

`NOT NULL` should be your default; every nullable column needs a *reason* ("score is unknown until first order"). NULLs complicate every comparison (lesson 13) and every unique constraint (they don't conflict!).

## Worked example — a production-shaped table

```sql
CREATE TABLE sales.invoices (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id   UUID NOT NULL DEFAULT gen_random_uuid() UNIQUE,  -- shown in URLs
    customerid  INT NOT NULL REFERENCES sales.customers (customerid),
    total       NUMERIC(12,2) NOT NULL CHECK (total >= 0),
    currency    TEXT NOT NULL DEFAULT 'EUR',
    issued_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    due_date    DATE NOT NULL
);
```

## Exercises

1. Run the float vs numeric experiment above. Now inspect `salesdb`: `products.price` and `orders.sales` are plain `INT` — whole units only. Try `INSERT INTO sales.products VALUES (110, 'Sub-cent gadget', 'Toys', 19.99);` and then `SELECT` the row — what happened to the price? (Integer *assignment casts round*, they don't truncate.) Fix the column: `ALTER TABLE sales.products ALTER COLUMN price TYPE NUMERIC(10,2);` — when is this easy on a small table, and what does it require on a huge one (a table rewrite — plan for it)?

2. Insert the same instant into a `TIMESTAMP` and a `TIMESTAMPTZ` column, switch your session timezone (`SET timezone = 'America/New_York'`), and `SELECT` both. What changed, what didn't, and why?

3. A bug report says: *"orders placed after 11pm Berlin time show up under the next day for our US reports."* Which type choice causes this class of bug, and how does `TIMESTAMPTZ` fix it?

4. Create a table twice — once with `SERIAL` PK, once with `GENERATED ALWAYS AS IDENTITY` — and inspect both with `\d`. What extra object does `SERIAL` create? Why is `GENERATED ALWAYS` safer than `GENERATED BY DEFAULT` for app inserts?

5. Add a `uuid` column with `gen_random_uuid()` default to `sales.customers`. When would you expose this id in an API instead of `customerid`? (Think: what does `/customers/7` leak?)

6. **Predict before you run:** a table has `email TEXT UNIQUE`. You insert `NULL` email twice. Does the second insert fail? Verify, then explain using lesson 13's NULL semantics. How would a partial unique index (lesson 23) on `email IS NOT NULL` behave differently?
