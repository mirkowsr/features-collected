# Lesson 24.5 — Concurrency in practice: locking patterns & retries

**Goal:** Survive two users clicking at the same time — the locking patterns behind "the last item in stock".

---

## Theory

Lesson 24 gave you ACID, isolation levels, and MVCC. This lesson is the applied part: what to actually *write* when two transactions touch the same row.

### The lost update

The classic failure under `READ COMMITTED` (Postgres default):

```
Tx A                          Tx B
SELECT score WHERE id=1       SELECT score WHERE id=1
  → 350                         → 350        (both read the same value)
score = 350 + 10
UPDATE ... SET score = 360
COMMIT
                              score = 350 + 20
                              UPDATE ... SET score = 370
                              COMMIT
-- A's +10 is silently LOST. Correct total: 380. Stored: 370.
```

No error, no warning — just wrong data. Three defenses:

### Defense 1: Atomic single-statement update

Never read-modify-write when the write can be done in the database:

```sql
UPDATE sales.customers SET score = score + 10 WHERE customerid = 1;
```

The database does read-and-write under the row lock, so concurrent increments serialize correctly. This fixes most real cases (counters, stock, balances).

### Defense 2: SELECT ... FOR UPDATE (pessimistic locking)

When you *must* read a value, branch in app code, then write — lock the row first:

```sql
-- setup: salesdb products have no stock column yet — add one
ALTER TABLE sales.products ADD COLUMN quantity INT NOT NULL DEFAULT 10;

BEGIN;
SELECT quantity FROM sales.products WHERE productid = 101 FOR UPDATE;
-- row is now locked; other FOR UPDATE/UPDATE writers block here
-- app checks: quantity >= 3 ?
UPDATE sales.products SET quantity = quantity - 3 WHERE productid = 101;
COMMIT;
```

| Variant | Behaviour |
|---------|-----------|
| `FOR UPDATE` | wait for the lock (default) |
| `FOR UPDATE NOWAIT` | fail immediately with an error — good for retries |
| `FOR UPDATE SKIP LOCKED` | skip locked rows — the foundation of **job queues** |

### Defense 3: Optimistic locking (version column)

For long gaps between read and write (a user editing a form for 5 minutes), holding a lock is impossible. Instead, detect interference at write time:

```sql
ALTER TABLE sales.products ADD COLUMN version INT NOT NULL DEFAULT 0;

-- read: productid 101, price 69.99, version 7   (user edits in UI... minutes pass)
UPDATE sales.products
SET price = 74.99, version = version + 1
WHERE productid = 101 AND version = 7;   -- the version we saw

-- if this updates 0 rows, someone else changed it first → reload and retry
```

No locks held; the `WHERE version = 7` guard makes the update conditional on "nobody touched it since I looked". ORMs do this for you if a `version` column exists.

### Deadlocks

Two transactions locking the same rows **in different orders**:

```
A locks row 1, wants row 2
B locks row 2, wants row 1   → Postgres kills one with: deadlock detected
```

Prevention: always touch rows in a **consistent order** (e.g. ascending id), keep transactions short. Your app should retry deadlocked transactions — the error code is `40P01`.

### Retry discipline

Deadlocks and serialization failures are **normal**, not bugs. Production rule: catch them, retry the whole transaction (a few times, with a small delay). Never retry a transaction that failed for a *logic* error (constraint violation) — that will fail forever.

## Worked example — the last item in stock

```sql
-- WRONG (races): check and decrement in two unlocked statements
-- SELECT quantity FROM sales.products WHERE productid = 101;  -- app sees 1
-- UPDATE sales.products SET quantity = 0 WHERE productid = 101;

-- RIGHT: atomic conditional decrement
UPDATE sales.products
SET quantity = quantity - 1
WHERE productid = 101 AND quantity >= 1
RETURNING quantity;
-- 0 rows returned → out of stock; 1 row → sold, new quantity included
```

## Exercises

1. In two `psql` sessions, run the lost-update script above verbatim (open `BEGIN` in both, interleave the steps). Confirm the wrong total. Then repeat with the atomic `SET score = score + ?` version in both sessions — what changed?

2. Two sessions: both run `SELECT ... FOR UPDATE` on the same customer row inside `BEGIN`. What does the second session do while the first holds the lock? Commit the first and watch the second. Then retry the second with `NOWAIT` — what error do you get?

3. **Build a mini job queue:** add 10 rows to a `jobs` table. From two sessions, repeatedly run `DELETE FROM jobs WHERE id = (SELECT id FROM jobs ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *;` until empty. Did any job run twice? Why is `SKIP LOCKED` the key ingredient?

4. Add the `version` column to `sales.products`. Simulate two "edit form" sessions: both read version 7, both try to `UPDATE ... WHERE version = 7`. How many rows does each update? What should the loser's application do next?

5. Cause a deadlock on purpose: session A updates customer 1 then 2; session B updates customer 2 then 1 — interleave them. Note the error and which transaction survives. Rewrite both in ascending-id order and confirm the deadlock disappears.

6. **Predict before you run:** at default `READ COMMITTED`, a transaction does `SELECT count(*)` from `orders`, waits 10 seconds (other sessions insert rows), then `SELECT count(*)` again in the *same* transaction. Same number or different? Why? (Connect this to lesson 24's anomaly table, and to why `REPEATABLE READ` exists.)
