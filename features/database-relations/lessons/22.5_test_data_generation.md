# Lesson 22.5 — Generating realistic test data (so performance lessons actually work)

**Goal:** Create a large `salesdb` copy (100k+ rows) with `generate_series()` — because on 10 rows, lessons 23 and 27 can't demonstrate anything.

---

## Theory

Lessons 23 (indexes) and 27 (execution plans) keep warning: *"on a tiny table the planner correctly prefers Seq Scan."* That means on the 10-row `salesdb`, **you cannot observe indexes working**. The fix is data volume — and Postgres can generate it in SQL, no external tools.

### The toolkit

| Function | Returns | Use |
|----------|---------|-----|
| `generate_series(start, stop)` | a set of integers | row counts, ids, date series |
| `generate_series(ts, ts, interval)` | a set of timestamps | dates spread over time |
| `random()` | float in [0, 1) | jitter, weighted picks |
| `floor(random() * n) + 1` | int in [1, n] | random FK assignment |
| `(ARRAY[...])[i]` | one element by index | random category/status |
| `md5(x)` | hex hash of text | fake unique-ish strings |
| `INSERT ... SELECT` (lesson 07) | rows from a query | load the generated set |

### Recipe

```sql
INSERT INTO sales_big.orders (orderid, customerid, productid, orderdate, quantity, sales)
SELECT
    g                                    AS orderid,
    floor(random() * 10000) + 1          AS customerid,   -- random existing customer
    floor(random() * 500) + 1            AS productid,
    date '2023-01-01' + (random() * 730)::int AS orderdate, -- spread over 2 years
    floor(random() * 10) + 1             AS quantity,
    round((random() * 500)::numeric, 2)  AS sales
FROM generate_series(1, 200000) AS g;
```

200k rows in about a second. Deterministic alternative: replace `random()` with functions of `g` (`g % 10000`, etc.) for reproducible datasets.

### After generating: ANALYZE

The planner needs fresh **statistics** (lesson 27) to notice your new rows. Always finish a generation script with:

```sql
ANALYZE sales_big.orders;
```

### Realism tips

- **Skew beats uniform.** Real data has hot customers and dead products: `floor(abs(random() - random()) * 10000) + 1` creates a triangular (skewed) customer distribution.
- **Correlate columns.** `quantity` and `sales` should relate (`sales ≈ quantity × price`), or joins/aggregates produce nonsense.
- **Spread dates with gaps** if you want realistic `date_trunc` histograms.

## Worked example — the full script

The course ships [`datasets/postgres/generate-big-salesdb.sql`](../../datasets/postgres/generate-big-salesdb.sql). Run it next to your small database:

```bash
psql -U postgres -h localhost -f datasets/postgres/generate-big-salesdb.sql
```

It creates a separate `bigsalesdb` database with schema `sales` (same table shapes), loads 10k customers / 500 products / 1k employees / **200k orders**, and runs `ANALYZE`. Your small `salesdb` stays untouched for the theory lessons.

Sanity check:

```sql
SELECT count(*) FROM sales.orders;             -- 200000
SELECT min(orderdate), max(orderdate) FROM sales.orders;
SELECT customerid, count(*) FROM sales.orders
GROUP BY customerid ORDER BY count(*) DESC LIMIT 5;   -- hot customers visible
```

## Exercises

1. Generate 50,000 additional orders *dated in the future* (next 30 days) into `bigsalesdb`. Which `generate_series`/`random` expression produces the dates? Then re-check `min`/`max(orderdate)`.

2. Modify the recipe so 1% of customers place 30% of orders (a "whale" distribution). Hint: `CASE WHEN random() < 0.3 THEN floor(random()*100)+1 ELSE floor(random()*10000)+1 END`. Verify with the hot-customers query above.

3. Generate a `sales.order_items` table (orderid, line_no, productid, qty) with **1–5 lines per order** for the first 1,000 orders — one `INSERT` using `generate_series(1,1000) CROSS JOIN LATERAL generate_series(1, ...)`. (CROSS JOIN + a per-row random series; lesson 10's join types apply to set-returning functions too.)

4. Run a heavy aggregation (`SELECT customerid, sum(sales) FROM sales.orders GROUP BY customerid`) with `EXPLAIN ANALYZE` **before** and **after** `ANALYZE sales.orders;`. Does the plan change? Why might it not, on a freshly loaded table? (Hint: autovacuum may have already analyzed it — check `pg_stat_user_tables.last_analyze`.)

5. Make it deterministic: rewrite the orders generator using only `g` (no `random()`) so two runs produce byte-identical tables. Why would a *reproducible* dataset matter for comparing query plans across experiments?

6. **Predict before you run:** insert 200k rows with `orderstatus` chosen as `'Delivered'` for 80% of rows (weighted random). Now run the lesson-23 exercise on a **partial index** `WHERE orderstatus = 'Pending'` — how big is the partial index compared to a full one, and when does the planner use it?
