# Lesson 07.6 — Bulk operations: multi-row INSERT, UPDATE FROM, COPY

**Goal:** Move thousands of rows efficiently — seeds, imports, and batch corrections.

---

## Theory

One row per statement is fine for a web request. It's a disaster for 50,000 rows: every statement is a round-trip, a parse, and (without a transaction) its own commit.

| Technique | Use | Speed |
|-----------|-----|-------|
| `INSERT ... VALUES (...), (...), ...` | up to a few thousand rows per statement | good |
| `INSERT ... SELECT` (lesson 07) | copy/transform between tables | good |
| `UPDATE ... FROM` | batch-update from a staging table | good |
| `COPY table FROM 'file'` | CSV imports, migrations, ETL | **fastest by far** |

### Multi-row INSERT

```sql
INSERT INTO sales.products (productid, product, price, category)
VALUES
  (106, 'Helmet', 89.99, 'Accessories'),
  (107, 'Gloves', 24.50, 'Accessories'),
  (108, 'Water Bottle', 12.00, 'Sports');
```

One statement, one round-trip, one commit. Chunk huge imports into batches of ~1,000 rows rather than one mega-statement.

### UPDATE ... FROM — batch corrections via a staging table

The real-world pattern: load external data into a **staging table**, then merge:

```sql
-- staging table with new prices
CREATE TEMP TABLE price_updates (productid INT, new_price NUMERIC(10,2));

UPDATE sales.products p
SET price = pu.new_price
FROM price_updates pu
WHERE p.productid = pu.productid;
```

Note: the target table gets an alias, and the join condition goes in `WHERE`. Wrong join = wrong updates on *every* row — preview first (lesson 07's habit).

### COPY — the import/export workhorse

```sql
-- server-side: file must be readable by the Postgres server process
COPY sales.products FROM '/data/products.csv' WITH (FORMAT csv, HEADER true);

-- client-side via psql: file is on YOUR machine
\copy sales.products FROM './products.csv' WITH (FORMAT csv, HEADER true)

-- export
\copy (SELECT * FROM sales.orders WHERE orderdate >= '2025-01-01') TO './orders_2025.csv' WITH (FORMAT csv, HEADER true)
```

`COPY` streams rows with minimal overhead — orders of magnitude faster than equivalent `INSERT`s.

### Wrap it in a transaction

Bulk jobs are all-or-nothing candidates (lesson 24):

```sql
BEGIN;
\copy ...
UPDATE ... FROM ...;
-- sanity checks here
COMMIT;   -- or ROLLBACK if counts look wrong
```

## Worked example — import, stage, merge

```sql
BEGIN;

CREATE TEMP TABLE staging_customers (
  customerid INT, firstname TEXT, lastname TEXT, country TEXT, score INT
);

-- needs a real CSV on your machine — or export one first with `\copy ... TO`
\copy staging_customers FROM './new_customers.csv' WITH (FORMAT csv, HEADER true)

SELECT count(*) FROM staging_customers;   -- expected count?

-- upsert-merge into the real table (lesson 07.5)
INSERT INTO sales.customers (customerid, firstname, lastname, country, score)
SELECT customerid, firstname, lastname, country, score FROM staging_customers
ON CONFLICT (customerid) DO UPDATE
  SET firstname = EXCLUDED.firstname,
      lastname  = EXCLUDED.lastname,
      country   = EXCLUDED.country,
      score     = EXCLUDED.score;

COMMIT;
```

## Exercises

1. Insert 5 new products with **one** multi-row `INSERT`. Then insert 5 more with 5 separate statements inside explicit transactions. (You can't easily time 5 rows — but imagine the commit overhead ×50,000.)

2. Create a `staging_products` temp table and fill it from `sales.products` with a 10% price increase (`INSERT INTO staging_products SELECT productid, round(price * 1.1, 2) FROM sales.products;`). Then `UPDATE ... FROM` to apply the new prices. Preview the join with a `SELECT` first — which rows will change? (If you have CSVs of your own, the same flow works with `\copy` into staging.)

3. Export all `sales.orders` to CSV with `\copy ... TO`. Delete all rows from a *copy* of the table (`sales.orders_backup`), then re-import with `\copy ... FROM`. Verify counts match.

4. Wrap exercise 2 in a transaction, run it, check the results, then `ROLLBACK`. Confirm prices are unchanged. When is a bulk job *not* a good fit for one big transaction? (Think: lock duration, and what a 6-hour import rollback means.)

5. **Predict before you run:** `\copy` a CSV that contains one row violating a `CHECK` constraint (lesson 06). How many rows load — all up to the bad one, or none? Verify, and explain what that means for your import error-handling strategy.

6. Compare `INSERT ... SELECT` vs `COPY` conceptually: both move data in bulk. Which one can read from *your laptop's* filesystem, and which one can read from *another table's live data*? When would you chain them?
