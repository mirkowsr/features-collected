# Lesson 04.5 — Practical modeling patterns (soft deletes, timestamps, generated columns)

**Goal:** Apply modern table-design conventions you'll use in real applications, on top of the normalization rules from lesson 04.

---

## Theory

Normalization (lesson 04) tells you *where* data should live. These patterns tell you *how* production tables are usually shaped around it.

### The patterns

| Pattern | What it is | Why |
|---------|-----------|-----|
| **Audit timestamps** | `created_at TIMESTAMPTZ DEFAULT now()`, `updated_at` on every table | debugging, sorting, sync, "when did this change?" |
| **Soft delete** | `deleted_at TIMESTAMPTZ` instead of `DELETE` | preserve history, undo mistakes, keep FK references valid |
| **Generated column** | a column computed from other columns, stored or virtual | keep derived values consistent (no app-code drift) |
| **Surrogate vs natural key** | `id SERIAL/IDENTITY` vs a real-world value as PK | surrogates never change; natural keys sometimes do |

### Soft deletes

```sql
-- instead of: DELETE FROM sales.customers WHERE customerid = 5;
UPDATE sales.customers SET deleted_at = now() WHERE customerid = 5;

-- every query must now filter them out:
SELECT * FROM sales.customers WHERE deleted_at IS NULL;
```

Trade-offs:

- ✅ History preserved, deletes are reversible, FKs from other tables stay valid.
- ❌ Every query must remember `WHERE deleted_at IS NULL` (a view, lesson 22, helps).
- ❌ `UNIQUE` constraints now conflict with "deleted" rows — a deleted `kevin@x.com` still blocks a new one (a **partial index**, lesson 23, fixes this).

### Generated columns

```sql
ALTER TABLE sales.orders
  ADD COLUMN total NUMERIC(10,2) GENERATED ALWAYS AS (quantity * sales) STORED;
```

The value is computed by the **database**, always correct, impossible to forget in app code. Use for derived values that must be queryable/indexable (full name, totals, search vectors).

### The `updated_at` problem

Postgres does **not** update `updated_at` automatically — `ON UPDATE CURRENT_TIMESTAMP` is a MySQL feature. Your options:

1. Set it in application code on every `UPDATE` (simple, usual ORM choice).
2. A trigger (lesson 26).

## Worked example — retrofit `sales.orders`

```sql
ALTER TABLE sales.orders
  ADD COLUMN created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  ADD COLUMN deleted_at TIMESTAMPTZ;

-- "delete" order 10 softly
UPDATE sales.orders SET deleted_at = now() WHERE orderid = 10;

-- every query for "current" orders now filters explicitly:
SELECT count(*) FROM sales.orders WHERE deleted_at IS NULL;   -- 9
```

(Lesson 22 shows how a `VIEW` can hide the `deleted_at IS NULL` filter; lesson 23 shows how a *partial index* keeps soft-deleted rows out of unique constraints.)

## Exercises

1. Apply the same three columns to `sales.customers`. Tip: real migration scripts are re-runnable — use `ADD COLUMN IF NOT EXISTS` (lesson 06 will also have you add a `created_at` — with `IF NOT EXISTS`, re-running is a no-op instead of an error).

2. Write a generated column `full_name` on `sales.customers` as `firstname || ' ' || lastname`. What happens when `lastname IS NULL`? Fix it with `COALESCE` (lesson 13).

3. Soft-delete one customer, then write the query "all customers" twice: once naively, once correctly. What does the naive version return that it shouldn't?

4. `ordersarchive` (lesson 05) has no FKs and allows duplicates — arguably it *is* a soft-delete/history pattern done at table level. Compare "archive table" vs "soft-delete column": which preserves more integrity, and which costs more on every query?

5. Soft-delete a customer named like an existing one, then try to create a `UNIQUE` index on `customers(firstname)` — why does the soft-deleted row still block a new customer with that name? Look ahead to lesson 23 and write the **partial** unique index (`WHERE deleted_at IS NULL`) that allows re-using the name. (Keep this index in mind — lesson 23's exercise 3 meets it again.)

6. **Design decision:** an order's `shipaddress` is copied onto the order row instead of always joining to the customer's current address. Which normalization rule does this break, and why is breaking it *correct* here? (Hint: what should an old order's address show after the customer moves?)
