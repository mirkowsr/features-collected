# Lesson 07.5 — RETURNING & upserts (ON CONFLICT)

**Goal:** Get data back from writes in one round-trip, and handle "insert or update" atomically.

---

## Theory

### RETURNING — the write that talks back

Postgres can return the affected rows from any `INSERT`, `UPDATE`, or `DELETE` — including values you never sent (generated keys, defaults):

```sql
INSERT INTO sales.customers (customerid, firstname, country)
VALUES (8, 'Tara', 'USA')
RETURNING customerid;   -- add created_at to the list if you did lesson 04.5
```

Without it you need two round-trips (`INSERT`, then `SELECT` to learn the new id). With `IDENTITY`/default-heavy schemas (lesson 06.5), `RETURNING` is how you learn what the database decided.

Common uses:

- `INSERT ... RETURNING id` — get the generated key.
- `UPDATE ... RETURNING *` — return the row as it is *now* (with triggers/defaults applied).
- `DELETE ... RETURNING customerid` — confirm exactly which rows were removed.

### Upsert — INSERT ... ON CONFLICT

"Create this row; if it already exists, update it instead" is a constant need (sync jobs, imports, idempotent APIs). Naive app code does `SELECT` then branch — which **races** (two requests both see "missing", both insert, one crashes). The atomic version:

```sql
INSERT INTO sales.products (productid, product, price, category)
VALUES (106, 'Helmet', 89.99, 'Accessories')
ON CONFLICT (productid) DO UPDATE
  SET price = EXCLUDED.price,
      category = EXCLUDED.category;
```

| Piece | Meaning |
|-------|---------|
| `ON CONFLICT (productid)` | which unique constraint/index to check |
| `DO NOTHING` | skip the row silently |
| `DO UPDATE SET ...` | update the existing row instead |
| `EXCLUDED.col` | the value we *tried* to insert |

Requires a matching `UNIQUE`/`PRIMARY KEY` constraint on the conflict target.

### Idempotency

An operation is **idempotent** if running it twice has the same effect as once. Upserts make retries safe: if your API times out and the client retries, `ON CONFLICT` absorbs the duplicate instead of erroring.

---

## Worked example — sync a price list idempotently

```sql
-- run this as many times as you like; the table ends in the same state
INSERT INTO sales.products (productid, product, price, category)
VALUES
  (106, 'Helmet', 89.99, 'Accessories'),
  (107, 'Gloves', 24.50, 'Accessories')
ON CONFLICT (productid) DO UPDATE
  SET price = EXCLUDED.price
RETURNING productid, price;
```

## Exercises

1. Insert a new customer and return only `customerid`. Then do the same insert without `RETURNING` — how would your application code learn the id, and why is that worse (think: two round-trips, sequences advancing on failed inserts)?

2. Write an `UPDATE` that raises every German customer's score by 10 and returns `firstname, score`. Why is the returned `score` guaranteed to be the *new* value?

3. Delete the test rows you added to `sales.products` in earlier exercises, returning the deleted rows so you can paste them back in if you regret it.

4. Upsert product `106` three times with different prices using `ON CONFLICT ... DO UPDATE`. After each run, `SELECT` — what happens to `productid`, and what would have happened with plain `INSERT` on the second run?

5. Change exercise 4 to `DO NOTHING`. Re-run with a different price. Which version would you want for (a) importing a product catalog, (b) recording a click event, (c) a "create user if missing" endpoint?

6. **Race condition:** two requests run `SELECT 1 FROM products WHERE productid = 106;` simultaneously, both find nothing, both `INSERT`. What happens to the second one without `ON CONFLICT`? Explain why `ON CONFLICT` makes this safe without any locking in app code.

7. **Predict before you run:** does `ON CONFLICT DO UPDATE` fire triggers (lesson 26) as an INSERT, an UPDATE, or both? How could you verify with an `audit_log` trigger?
