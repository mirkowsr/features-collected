# Lesson 27.5 — Finding slow queries: pg_stat_statements, BUFFERS & maintenance

**Goal:** Lesson 27 taught you to *read* plans. This lesson: how to *find* the queries worth reading plans for, and keep the database healthy underneath them.

---

## Theory

Optimizing what you *think* is slow is guessing. Production databases tell you the truth — you just have to ask.

### pg_stat_statements — the flight recorder

An extension that tracks execution stats for every query (normalized, so `WHERE id = 1` and `WHERE id = 2` count as one):

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
-- requires shared_preload_libraries = 'pg_stat_statements' in postgresql.conf + restart
```

The top-10 query you run in every incident:

```sql
SELECT calls,
       round(mean_exec_time::numeric, 2)  AS mean_ms,
       round(total_exec_time::numeric, 0) AS total_ms,
       left(query, 80)                    AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

Read it as: **total time** = where your database's life goes; **mean time** = what users feel per call. A 2ms query called 1M times often beats a 5s query called twice. `calls` + `mean` + `total` together tell you which lever exists: optimize the query, or call it less (caching, N+1 fixes).

### EXPLAIN (ANALYZE, BUFFERS) — the full X-ray

Lesson 27 used `EXPLAIN ANALYZE`. Add `BUFFERS` to see I/O, the real killer:

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM sales.orders WHERE customerid = 42;
```

| Output | Meaning |
|--------|---------|
| `shared hit=N` | blocks served from cache (fast) |
| `read=N` | blocks read from **disk** (slow) |
| high `read` + `Rows Removed by Filter` | you're scanning junk → missing index |

Also: compare the plan's estimated `rows=` to `actual rows`. Estimates off by 100×+ usually mean **stale statistics** — the planner is optimizing for a table that no longer exists.

### VACUUM, ANALYZE, bloat

| Command | What | Why you care |
|---------|------|--------------|
| `ANALYZE t` | refresh planner statistics | stale stats → wrong plans |
| `VACUUM t` | reclaim space from dead rows | Postgres UPDATEs/DELETEs leave dead versions (MVCC); bloat slows scans |
| `VACUUM FULL t` | rewrite the whole table compactly | locks the table! emergency only |
| autovacuum | does both automatically in the background | ✅ on by default — don't disable it |

Check what autovacuum has done for you:

```sql
SELECT relname, last_vacuum, last_analyze, n_dead_tup, n_live_tup
FROM pg_stat_user_tables
WHERE schemaname = 'sales'
ORDER BY n_dead_tup DESC;
```

## Worked example — find it, x-ray it, fix it

```sql
-- 1) find: what eats total time?
SELECT calls, round(mean_exec_time::numeric,2) AS mean_ms, left(query,60) AS q
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;

-- 2) x-ray the winner
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM sales.orders WHERE customerid = 42 ORDER BY orderdate DESC;

-- 3) fix, then re-run 2) and compare read/hit blocks and actual time
CREATE INDEX idx_orders_customer_date ON sales.orders (customerid, orderdate DESC);
```

## Exercises

1. Enable `pg_stat_statements` (on the course Docker setup: add `-c shared_preload_libraries=pg_stat_statements` to the container command, restart, then `CREATE EXTENSION`). Run a handful of queries from earlier lessons, then inspect the top-10 view. Which query has the best "total time vs mean time" ratio, and what does that ratio mean?

2. Generate load against `bigsalesdb`: run the same customer-lookup query in a loop (shell: `for i in $(seq 1 500); do psql -c "SELECT * FROM sales.orders WHERE customerid = $((RANDOM % 10000))"; done` — or your app's equivalent). Check `pg_stat_statements`: how many entries, and why did the 500 different `customerid` values collapse into one row?

3. Run the exercise-2 query with `EXPLAIN (ANALYZE, BUFFERS)` twice in a row. What changes in the buffer counts between the first and second run, and what does that tell you about Postgres caching?

4. In `bigsalesdb`, update 50% of `orders` rows, then inspect `pg_stat_user_tables.n_dead_tup`. Run `VACUUM ANALYZE sales.orders;` and look again. What happened, and what would repeated update-heavy workloads do to a table without autovacuum?

5. Force a bad plan: `SET enable_seqscan = off;` then `EXPLAIN ANALYZE` a query that *should* seq-scan (e.g. `WHERE orderstatus = 'Delivered'` — 80% of rows). Compare costs. What does this teach you about trusting the planner vs forcing it? (`RESET enable_seqscan;` when done.)

6. **Incident drill:** on `bigsalesdb`, a teammate reports "the orders endpoint got slow after launch week." Write the three diagnostic queries you'd run first (stats freshness, dead tuples, top-by-total-time) and say what each rules out.

7. **Predict before you run:** does `CREATE INDEX` on a 200k-row table block writes? Try inserting a row from a second session while creating an index on `sales.orders` in `bigsalesdb`. Then read about `CREATE INDEX CONCURRENTLY` — what's the trade-off?
